# Fresta Diamond

## Em uma frase

O **Fresta Diamond** é a implementação limpa, modular e verificável do núcleo
operacional do **Fresta Protocol**.

Não é outro projeto nem uma ontologia diferente. É o mesmo Fresta reconstruído
aos poucos a partir das partes que já provaram funcionar no protótipo atual,
mas com fronteiras claras entre memória, raciocínio, validação, decisão e
efeitos externos.

## Qual é o objetivo do Fresta Protocol?

Uma LLM consegue gerar linguagem e propor decisões, mas normalmente depende da
janela de contexto, mistura memória com atenção e pode confundir coerência com
verdade. O Fresta pretende fornecer a infraestrutura cognitiva persistente em
redor da LLM.

O objetivo não é guardar tudo nem substituir o modelo. É permitir que um
sistema:

- mantenha memória persistente fora da janela de contexto;
- recupere apenas o que é relevante para o objeto atual;
- distinga candidaturas, evidência, hipóteses, conhecimento confirmado e
  informação em quarentena;
- organize cartões por conceitos sem lhes atribuir ordens universais;
- derive papéis O1, O2 e O3 relativamente a cada objetivo;
- preserve proveniência, custos, alternativas excluídas e contradições;
- use a LLM quando é necessária interpretação ou decisão, sem lhe entregar a
  autoridade para validar a própria resposta;
- execute ferramentas e efeitos através de permissões limitadas;
- checkpointar, dormir e retomar trabalho sem fingir que o contexto é infinito;
- aprender e rever informação sem apagar silenciosamente a sua história.

Em termos simples:

```text
LLM = geração, interpretação e decisão proposta
Fresta = memória, estrutura, restrições, validação, execução e continuidade
```

Quanto mais estrutura útil o Fresta acumula, menos trabalho repetitivo a LLM
precisa de fazer. A LLM continua crucial para autonomia, mas opera sobre um
sistema que conhece os seus contratos e limites.

## A lógica ontológica

O Fresta é subordinado ao kernel ontológico, não o contrário.

- **Φ / PHI** representa incompletude constitucional: a abertura irredutível
  que torna possível distinguir e atualizar. Não é o nome de qualquer dado em
  falta.
- **F / FILTER** é seleção sob uma condição de persistência. Determinar algo
  admite uma possibilidade e exclui outras.
- **Φ+ / WITNESS** é o que sobrevive à filtragem e testemunha que a seleção não
  foi arbitrária para aquele objeto.
- **Φ- / COST** é o complemento excluído, que permanece auditável.
- **O1** é a manifestação delimitada no objeto atual.
- **O2** é a relação. Uma O2 forte inclui efeito da restrição, testemunho de
  retorno e custo excluído; sem isso existe apenas associação ou nomeação.
- **O3** é a restrição contextual de admissibilidade. Não é uma categoria fixa
  de cartão ou módulo.

As ordens são relativas ao objeto analisado. Um cartão, conceito, módulo ou
resultado pode ocupar papéis diferentes noutros objetivos. A hierarquia de
conceitos também não é uma hierarquia de ordens.

Uma análise estruturalmente fechada precisa de uma cadeia contextual não vazia e
auditável. Quando a profundidade é constitucional, a cadeia inclui também o
reconhecimento explícito de FILTER e Φ. Um modelo dizer `closed=true` nunca é
suficiente.

Essa fundamentação constitucional explícita é condicional à profundidade do
objetivo. Uma análise comum já situada depois de F ontológico pode fechar a sua
estrutura contextual em O1/O2/O3 sem voltar a derivar Φ e F. Nesse caso o eixo
constitucional fica `not_evaluated`, não `false`.

## O que é o Frankenstein?

Chamamos informalmente **Frankenstein** ao Fresta atual: a implementação onde as
ideias foram descobertas, combinadas e testadas rapidamente. Já contém memória,
cartões, conceitos, `/learn`, Web, REPL, blueprints, atenção, validação de três
ordens e muitas experiências úteis.

Ele continua importante:

- é a bancada experimental;
- contém comportamentos que ainda não foram extraídos;
- serve de fallback e referência comparativa;
- continua funcional enquanto o Diamante cresce.

O Frankenstein não será apagado só porque existe uma versão nova. Uma peça só
passa para o Diamante depois de ter um contrato claro e testes proporcionais ao
risco.

O destino final, porém, não é manter duas implementações principais. O Diamante
deve tornar-se autónomo e substituir o Frankenstein como implementação oficial
do **Fresta Protocol**. O Frankenstein permanece como arquivo, laboratório e
oráculo comparativo; não pode ser uma dependência necessária do runtime, dos
dados, da configuração nem das interfaces novas. Quando os critérios de
sucessão forem cumpridos, o **Diamond deixa de ser o nome do produto**: passa a
ser simplesmente o Fresta Protocol.

## O que é o Diamante em relação ao Fresta?

```text
Fresta Protocol
├── Kernel ontológico       regras e invariantes
├── Frankenstein           protótipo funcional e laboratório
└── Diamond                implementação modular e limpa, ainda WIP
```

O Diamante separa responsabilidades que antes podiam estar misturadas:

```text
objetivo delimitado
  -> blueprint de outcomes e capacidades
  -> registry de módulos disponíveis
  -> resolver de dependências
  -> plano tipado PROPOSED
  -> validação técnica VALIDATED ou REJECTED
  -> autorização de efeitos AUTHORIZED ou DENIED
  -> runtime
  -> artefactos imutáveis + relatório de fecho
```

Uma blueprint declara o resultado necessário, não nomes de providers nem uma
cadeia fixa de ficheiros. O controller deriva uma implementação usando módulos
compatíveis. Por isso, um provider pode ser substituído sem alterar a interface,
a blueprint ou o controller.

## Estado atual

O Diamond já é um runtime autónomo executável, embora ainda não seja a versão
completa do Fresta Protocol. Neste checkpoint existem **340 testes Diamond** e
**527 testes conjuntos** com o Frankenstein.

Esta é a última baseline global confirmada. Depois dela foram acrescentados os
contratos de perfil e personalidade, verificados por quatro testes focados; os
stores correspondentes e uma nova baseline global pertencem ao próximo
checkpoint.

### Kernel e execução

- contratos imutáveis para artefactos, módulos, operações, blueprints e planos;
- registry com `discover -> anti-entropy verify -> enable`, proveniência e
  bloqueio fail-closed de capacidades constitucionais;
- resolução e validação separadas de DAGs tipados, com substituição de providers;
- `EffectBroker` com grants limitados e recusa de efeitos não autorizados;
- fecho técnico, estrutural, constitucional e epistémico em eixos distintos;
- journal e arquivos append-only verificados, checkpoints e retoma limitada.

### `/learn`, memória e conceitos

- `/learn` atravessa workspace, controller, avaliação LLM limitada, reparação,
  Gatekeeper e commit atómico em memória autónoma;
- `LearningCommit` persiste cristais e Φ− em conjunto, sem apagar propostas
  excluídas nem confundir retrieval com confirmação;
- conceitos nativos versionados com assinaturas, pertenças, aliases, pais sem
  ciclos, candidaturas, evidência e validação separadas;
- pesquisa conceptual externa mediada pelo `EffectBroker`, source units sem
  autoridade e retorno obrigatório pelo `/learn` antes de sustentar conceitos;
- diversidade de fontes, cobertura, budget e decisões explícitas de paragem;
- retrieval relativo ao objetivo sobre memória, conceitos, folhas e Φ−, com
  papéis O1/O2/O3 contextuais em vez de ordens fixas nos objetos.

### Atenção e workspace

- memória de atenção multi-contexto append-only, com foreground, suspensão,
  reativação, arquivo e abandono sem apagar história;
- projeção por budget, dependências fechadas, continuation checkpoints e
  processamento sequencial apenas dos refs pendentes;
- folhas cognitivas revisionadas, backlinks, hierarquia hash-bound, snippets,
  scratch ativa e representação dupla humano/canónica;
- decomposição lossless de objetos grandes e retoma automática pelos filhos
  exatos, com reconstrução SHA-256.

### Autonomia e interfaces

- serviço central extensível para `/learn`, atenção, conceitos e propostas de
  módulos;
- runner headless configurável com data root explícito e estado `INCOMPLETE`
  quando uma chamada não produz um artefacto válido;
- autonomia limitada de módulos: reutilização primeiro, proposta O1/O2/O3
  imutável depois, sem criar, instalar, admitir ou ativar código;
- REPL persistente fino sobre o mesmo serviço, com estado contínuo, JSON limpo
  por pipe e recuperação após erro ou interrupção;
- chat persistente ligado a retrieval, atenção e folha-transcrito, com binding
  selado e histórico hash-chained separado da memória validada;
- primeiro contrato separado de perfil do utilizador e personalidade do
  assistente: ambos são propostas versionadas sem autoridade de ativação;
- laboratório próprio, runners live para Qwen e comparação isolada com o
  Frankenstein sem dependência de runtime entre os dois projetos.

O mapa canónico de toda a documentação está em
[`docs/INDEX.md`](docs/INDEX.md). O estado exato, resultados dos testes e ponto
de retoma estão em [`docs/STATUS.md`](docs/STATUS.md).

## Web — Chat e Workspace Agent

O Web deverá oferecer duas experiências sobre o **mesmo kernel e o mesmo
serviço central**, não dois sistemas diferentes:

1. **Chat** — conversa persistente, memória, conceitos, perfil, personalidade e
   aprendizagem controlada.
2. **Workspace Agent** — trabalho persistente sobre projetos e tarefas, com
   planos, leitura de ficheiros, patches, testes, checkpoints e retoma; é o modo
   que permite usar o Fresta de forma semelhante ao Codex.

O Workspace Agent não recebe acesso irrestrito ao computador. Cada ação segue:

```text
LLM propõe
  -> controller deriva um plano
  -> firewall e permissões autorizam ou recusam
  -> EffectBroker executa numa fronteira limitada
  -> resultado e diff regressam ao sistema
  -> journal + checkpoint preservam a continuação
```

Os níveis iniciais de autoridade devem ser explícitos:

- `READ_ONLY`: observar projeto, estado e resultados;
- `PATCH`: propor e aplicar alterações dentro do workspace autorizado;
- `TEST`: executar comandos de verificação permitidos;
- `AGENT`: encadear passos aprovados com budgets, checkpoints e sleep;
- efeitos externos — rede, email, publicação, instalação ou credenciais —
  continuam a exigir grants próprios e autorização explícita.

Cada projeto deve possuir scope, memória de atenção, folhas, journal e secrets
isolados. Conteúdo de ficheiros, terminal, Web ou email é tratado como dado não
confiável, nunca como instrução com autoridade. O Web limita-se a representar
estado, pedidos de aprovação, atividade, diffs e resultados do serviço central.

## Plano de sucessão: Diamond → Fresta Protocol

O Diamond pode assumir o nome **Fresta Protocol** quando cumprir estes critérios:

1. arrancar num repositório limpo sem imports, paths, processos, configuração ou
   dados obrigatórios do Frankenstein;
2. possuir stores, migrações, providers, comandos, REPL e Web próprios;
3. executar learn, chat, atenção, conceitos, perfis e manutenção através dos
   mesmos contratos, Gatekeepers e fronteiras de autoridade;
4. isolar e revogar efeitos externos e módulos comunitários;
5. aceitar dados do Frankenstein apenas por um importador opcional, auditado e
   reversível;
6. demonstrar paridade ou melhoria nos benchmarks relevantes;
7. passar instalação limpa, documentação e testes sem o projeto antigo presente.

A promoção não significa embutir o Frankenstein no Diamond. Significa renomear
e publicar o runtime autónomo como Fresta Protocol. O Frankenstein permanece
como laboratório histórico, arquivo de experiências e fonte opcional de casos
de regressão.

`fresta_diamond`, separando-o do package Frankenstein `fresta`. O
`pyproject.toml` principal inclui `diamond/src` e `diamond/tests` na configuração
de testes, por isso a suite comum continua a verificar os dois sistemas sem
misturar os seus packages nem duplicar ficheiros. O empacotamento do Diamante é
definido apenas pelo seu próprio `diamond/pyproject.toml`.

## Arranque rápido

Para abrir o REPL com a Qwen local configurada por defeito:

```powershell
cd C:\Users\User\fresta-novo\diamond
python run_repl.py --data-root .\local-repl-data
```

O data root é sempre explícito: o Diamond não infere nem abre a `data/` do
Frankenstein. Dentro do REPL, `/help` lista os comandos centralizados e `/exit`
termina apenas a interface. Mais detalhes em [`docs/REPL.md`](docs/REPL.md).

Para executar só um comando, incluindo operações completamente offline:

```powershell
python run_commands.py --data-root .\local-command-data --command "/help"
```

Para testar apenas o Diamante a partir da raiz do repositório:

```bash
python -m pytest diamond/tests -q
```

Para runners live especializados e configuração da Qwen local, consultar
[`docs/QWEN-RUNNER.md`](docs/QWEN-RUNNER.md).

Para executar a baseline completa sem chamar a LLM:

```bash
cd diamond
python scripts/run_benchmark.py --all
```

O protocolo de comparação e atualização deliberada de baselines está em
[`docs/TEST-LAB.md`](docs/TEST-LAB.md).

O contrato da memória autónoma está em
[`docs/LEARNING-MEMORY.md`](docs/LEARNING-MEMORY.md).

Para comparar as duas implementações sem chamar a rede:

```bash
cd diamond
python scripts/run_cross_benchmark.py --all
```

Os runners que suportam reparação podem propor até três revisões limitadas com
`--repair-attempts`; uma revisão só é criada quando a anterior não satisfaz os
contratos exigidos por esse fluxo.

Também é possível entrar em `diamond/` e correr `python -m pytest -q` usando a
configuração isolada do subprojeto.

## Regra de desenvolvimento

Cada novo corte do Diamante deve:

1. corresponder a uma necessidade real do Fresta;
2. declarar contratos e autoridade antes de chamar providers;
3. preservar a distinção entre nomeação e validação;
4. representar lacunas finitas sem lhes chamar PHI;
5. possuir testes determinísticos e adversariais;
6. ser comparado com o Frankenstein quando substituir comportamento existente;
7. atualizar `docs/STATUS.md` sem esconder limitações.
